# WP-05 · Staging (efterhandsbeskrivning)

Branch: `wp/WP-05-staging` · Status: **byggd, väntar på granskning** · Beror på: WP-00 (☑).
Körd i egen worktree (`OrdenaGroup-wt/wp05-staging`), inget mot moln lokalt.

---

## 1. Mål

En avgränsad staging-miljö att granska agenternas arbete i, skild från produktion:
ett separat Supabase-projekt (`sa-east-1`) och ett Vercel-projekt (`gru1`), där
databasmigrationer sköts av GitHub Actions vid push till `main` — aldrig av en agent
(CLAUDE.md, hård regel 8). Det här är en avgränsning av BACKLOG:s ursprungliga
WP-05-rad ("Deploy + observabilitet … Sentry, PostHog"): den delen byggs i ett senare
arbetspaket.

## 2. Scope

**Med i det här paketet:**
- GitHub Actions-workflow som länkar mot staging-projektet, kör `db push` (och,
  bara manuellt, `db reset --linked`), och kör pgTAP mot molnet (`test db --linked`).
- `vercel.json` (region `gru1`).
- Öppna `/design-lab` i staging trots att Vercels miljö heter "production" där,
  styrt av en ny env-flagga `DESIGN_LAB`.
- `docs/tech/STAGING.md`: ägarens manuella steg (Supabase-projekt, hemligheter,
  Vercel-import, verifiering, vad som inte får göras).

**Uttryckligen utanför scope (skiljer sig från BACKLOG-radens ursprungliga omfattning):**
- Sentry och PostHog. Läggs till i ett senare arbetspaket när observabilitet
  prioriteras.
- Preview-miljöer per PR (Supabase-branch per PR). Inte byggt här.
- Riktiga tredjepartsnycklar (WhatsApp, Mercado Pago, Flow, Resend) i staging.
  `.env.example`/`docs/tech/STAGING.md` säger uttryckligen: tomt = fake-provider,
  och om de fylls i ska det peka mot sandbox, aldrig produktionskonton.
- Produktions-Vercel-projektet. Vercels "production"-miljö för det här projektet
  **är** staging tills vidare — det finns ingen separat riktig prod i Vercel än.
- Att faktiskt skapa Supabase-/Vercel-projekten eller lägga in hemligheterna.
  Det gör ägaren manuellt enligt `docs/tech/STAGING.md` — ingen agent har eller
  får de nycklarna.

## 4. Klart när

- `deploy-staging.yml` triggas av push till `main` på de tre path-mönstren, och av
  `workflow_dispatch` med boolesk input `reseed` (default `false`).
- Workflowen avslutar med ett tydligt fel om `STAGING_SUPABASE_ACCESS_TOKEN`,
  `STAGING_SUPABASE_DB_PASSWORD` eller `STAGING_SUPABASE_PROJECT_REF` saknas —
  inte tyst grönt.
- Workflowen kör `db push` alltid, `db reset --linked` bara vid manuell körning med
  `reseed=true`, och `test db --linked` efter `push`. Ingen `set -x`, inga
  hemligheter i loggen.
- `checkout`/`setup-node` är SHA-pinnade till samma versioner som `ci.yml`
  (`persist-credentials: false`, `.nvmrc`, npm från `packageManager`).
- `isDesignLabEnabled` är öppen i produktion om och bara om `DESIGN_LAB === "1"`,
  annars oförändrat beteende (öppen utanför `VERCEL_ENV=production`). Täckt av
  `gate.test.ts`. `proxy.ts` och `design-lab/layout.tsx` läser samma flagga.
- `vercel.json` sätter `regions: ["gru1"]` och inget annat.
- `docs/tech/STAGING.md` täcker (a)–(f) i sin helhet: skapa projektet, Supabase-
  inställningar, GitHub-hemligheter + första körning, Vercel-import, verifiering,
  vad staging är/inte är.
- `npm run typecheck && npm run lint && npm run format:check && npm run test &&
  npm run build` gröna, samt `npm run test:e2e` (port 3105) grönt. YAML och JSON
  validerade.
- Inget kört mot moln från agenten (ingen `link`/`db push`/`--linked` lokalt); det
  är blockerat av `.claude/settings.json` och kördes aldrig i den här sessionen.

## 5. Risker och antaganden att verifiera

- **`supabase test db --linked`:** verifierat med `npx supabase test db --help` i
  CLI 2.118.0 att flaggan finns. Har inte körts på riktigt mot ett molnprojekt (kan
  inte, se ovan). Om den skulle sluta fungera i en senare CLI-version: fall tillbaka
  till att köra filerna i `supabase/tests/` manuellt med `psql "$DATABASE_URL" -f
  <fil>` mot samma anslutning som `db push` använde (kommentar om detta finns i
  workflowen).
- **`supabase db push`/`link`/`db reset --linked` mot en riktig molndatabas:** inte
  körbart eller testbart härifrån (skyddsregler nekar lokalt, och det finns inget
  riktigt staging-projekt än). Mönstret (`link` med `SUPABASE_ACCESS_TOKEN` +
  `SUPABASE_DB_PASSWORD` i env, sedan `db push` utan ytterligare flaggor) följer
  Supabase CLI:s dokumenterade GitHub Actions-exempel, men **ägaren bör bevaka den
  första skarpa körningen** (Actions-fliken) och stämma av mot punkt (c)/(e) i
  `docs/tech/STAGING.md`.
- **Vercel:** `vercel.json` och miljövariabellistan i `STAGING.md` är skrivna utan
  tillgång till ett riktigt Vercel-projekt. Ägaren bör dubbelkolla att namnen på
  Environment Variables-fälten och Deployment Protection-alternativet stämmer med
  Vercels nuvarande UI när kontot faktiskt skapas.
- **`DESIGN_LAB` i ett framtida riktigt produktions-Vercel-projekt:** koden kan inte
  förhindra att någon råkar sätta `DESIGN_LAB=1` där (samma `VERCEL_ENV=production`
  delas). Det är dokumenterat som en regel i `.env.example`, `gate.ts` och
  `STAGING.md`, inte tekniskt spärrat — värt att komma ihåg när ett separat
  produktions-Vercel-projekt skapas.
- **333 pgTAP-tester** i `docs/tech/STAGING.md` är antalet som fanns i
  `docs/tasks/plans/WP-01.md` vid skrivandet; texten säger uttryckligen att antalet
  växer med nya migrationer, så det blir inte fel av sig själv, men bör stämmas av
  om det känns för gammalt.
