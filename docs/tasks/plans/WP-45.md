# WP-45 · Bekräftelse av bokningar + notiser

## 1. Mål
Bokningar från bokningssidan blir förfrågningar som företaget bekräftar eller nekar (om inte "bekräfta automatiskt" är på), med notiser i appen och rätt meddelanden till kunden. Rör F4, F5, F6, F7. **Klart när** (utökning av F7): en förfrågan ger kunden ett "solicitud recibida"-mejl inom 1 min; bekräftelse och 24 h-påminnelse skickas först efter bekräftelsen; tiden är blockerad hela tiden (F4: dubbelbokning omöjlig även för väntande).

## 2. Utanför scope
WhatsApp-mallar (egen WP för Meta, D-030) · realtid/push (sidan uppdateras vid navigering och fokus) · notistabell eller läst/oläst-status · behörigheter per person (WP-46) · handpenning + förfrågan i kombination (se FRÅGA 3) · väntelista/horas flash (WP-23/WP-30 avgör sin egen status).

## 4. Steg
1. **DB (db-engineer).** Migration A: `alter type booking_status add value 'requested'` (egen fil, enum-värdet kan inte användas i samma transaktion). Migration B: `no_overlap` återskapas med `status in ('requested','pending_payment','confirmed','completed')`; `businesses.auto_confirm_bookings boolean not null default false` + kolumngrant `update` till `authenticated`; index `(business_id, lower(period)) where status = 'requested'`. `npm run db:types`. OBS: "Sin confirmar" betyder redan *kunden har inte bekräftat* (`confirmed_by_customer_at`) — därför en ny status, inte återanvändning.
2. **Motor (scheduling-engineer).** `BLOCKING_STATUSES` får `requested`. `createBooking` med `actor.kind = 'customer'` sätter `requested` om inte `auto_confirm_bookings`; manuella bokningar är alltid `confirmed`. Ny `src/server/bookings/confirm.ts`: `confirmBooking` / `declineBooking` med villkorad update `where status = 'requested'` (idempotent, tål dubbelklick och kapplöpning med kundens avbokning). Nekad = `cancelled` + `cancel_reason = 'declined'`. Kundens flytt via `r/[token]` behåller `requested`. `BookingEvent` får `confirmed` och `declined`; `created` bär status.
3. **Meddelanden (integrations-engineer).** `created` + `requested`: kund `solicitudRecibida` (kanaler enligt `customerChannelsFor`), ägaren `nuevaSolicitud`, ingen påminnelse. `confirmed`: nuvarande bekräftelse + `recordatorio`. `declined`: kund `solicitudRechazada` med länk till `/{slug}`. Utgång (steg 6) → `solicitudVencida`. Mallar i `src/server/messaging/email/templates/booking.ts` och `sms/content.ts`.
4. **Texter (copywriter-es-cl).** Mallarna ovan, chipet för väntande (t.ex. "Por confirmar", ska skilja sig från "Sin confirmar"), knapparna Confirmar/Rechazar, notisklockans tomt läge, växeln i Ajustes med hjälptext, texten på `r/[token]` för en väntande bokning. es-CL + sv-SE.
5. **UI (ui-engineer).** Notismodell: härledd, ingen tabell — `listPendingRequests(businessId)` i `src/server/owner/requests.ts` = `status = 'requested' and lower(period) > now()`, sorterad på start. Klockan i toppraden: räknare + popover med Confirmar/Rechazar. Samma lista överst på Inicio (döljs när den är tom). Väntande bokningar i Agenda/Hoy: eget utseende (streckad kant + chip, bara tokens); agendans popover får Confirmar/Rechazar. Ajustes → Reservas: växeln "Confirmar reservas automáticamente". Server actions anropar `confirm.ts`, `revalidatePath` efter.
6. **Utgång (integrations-engineer + scheduling-engineer).** `expireRequests(now)` i `src/server/bookings/confirm.ts`, anropas från `/api/cron/outbox` (redan var 5:e min, D-030): `requested` vars start har passerat → `cancelled`, `cancel_reason = 'expired'`, event `declined` med orsak `expired`. (Se FRÅGA 1.)
7. **Docs.** `DATA_MODEL.md` (status, kolumn, constraint), `SCHEDULING.md`, D-033 i `DECISIONS.md`, BACKLOG ☑.

**D-033 (förslag):** Bokningar från bokningssidan skapas som `requested` och blockerar tiden tills företaget bekräftar/nekar eller tills de löper ut. "Bekräfta automatiskt" (av som standard) ger `confirmed` direkt. Notiser härleds ur bokningarna, ingen egen tabell i v1.

## 5. Tester
- **pgTAP:** två överlappande `requested` för samma personal → 23P01; `requested` + `confirmed` → 23P01; nekad `requested` frigör tiden; `auto_confirm_bookings` kan bara uppdateras av ägaren till det egna företaget (tenant A kan inte ändra B).
- **DB-test (Vitest):** kund bokar med automatisk bekräftelse av/på → `requested`/`confirmed`; `confirmBooking` samtidigt med kundens avbokning → exakt ett av dem lyckas; dubbelt `confirm` → ett event; ägare i B kan inte bekräfta A:s bokning; `expireRequests` rör bara passerade `requested`; start precis vid sommartidsbytet (första lördagen i april/september) går ut vid rätt instant.
- **Enhet:** enqueue: `requested` köar ingen påminnelse; `confirmed` köar påminnelse bara om start > 24 h bort; `declined` avbryter köade meddelanden. Mallar renderas i es-CL och sv-SE.
- **E2E:** boka på `/{slug}` → klockan visar 1 → Confirmar → chipet byter; Rechazar → tiden blir ledig igen på bokningssidan.
- **Visuell:** klockans popover, Inicio-listan och väntande kort i Agenda/Hoy mot baslinjer godkända i design lab.

## 6. Risker och öppna frågor
- `FRÅGA 1:` Utgång. Förslag: en förfrågan löper ut när starttiden passerat (enklast, kunden får "solicitud vencida"). Alternativ: löper ut X timmar före start eller 24 h efter att den skickats, så att kunden hinner boka annat. Vilket?
- `FRÅGA 2:` SMS i Sverige. Förslag: "förfrågan mottagen" och "tyvärr" följer samma kanaler som bekräftelsen (SE: e-post + SMS, CL: e-post). Alternativ: bara e-post, SMS enbart vid bekräftelse (billigare).
- `FRÅGA 3:` Tjänster med handpenning (WP-25, CL). Förslag: de hoppar över förfrågan (betalningen är kundens åtagande, `pending_payment` → `confirmed` som i dag). Alternativ: först bekräftelse, sedan betalningslänk.
- `FRÅGA 4:` Befintliga företag. Förslag: migrationen sätter `auto_confirm_bookings = true` för företag som redan finns (inget ändras för dem utan att de väljer det), nya får `false`.
- `FRÅGA 5:` Det finns ingen referensdesign för klockans popover och Inicio-listan. Förslag: ui-engineer bygger dem av befintliga komponenter i design lab, och du godkänner skärmdumpen som baslinje (hård regel 1).
- Risk: `alter type ... add value` går inte att rulla tillbaka, och alla `status`-switchar i UI måste hantera `requested` (typecheck fångar uttömmande switchar, SQL-filter `<> 'cancelled'` gör det inte → granska `agenda.ts`, `hoy.ts`, `inicio.ts`, kassan).

## 7. Klart när
- [ ] Förfrågan blockerar tiden (pgTAP) och syns som väntande i Agenda, Hoy, Inicio och klockan
- [ ] Bekräfta/Neka fungerar från klockan, Inicio och agendans popover, och är idempotent
- [ ] Rätt meddelanden: mottagen direkt, bekräftelse + påminnelse först efter bekräftelse, nekad/utgången med länk att boka igen
- [ ] Växeln i Ajustes, av som standard för nya företag
- [ ] `typecheck`, `lint`, `test`, `test:db`, `visual` gröna; D-033 och docs uppdaterade

## Ägarens svar (2026-09-30)
1. Utgång: en förfrågan löper ut 24 h efter att den skickades, dock senast 2 h före start (det som kommer först). Kunden får besked (samma kanal som "nekad").
2. SE: "förfrågan mottagen" bara e-post; "nekad"/"utgången" e-post + SMS. CL: e-post (+ WhatsApp när WP-22 finns).
3. Handpenning (CL): företaget bekräftar först, kunden får betalningslänken efter bekräftelse.
4. Befintliga företag: manuell bekräftelse som standard även för dem (bara pilot-/testföretag finns).
5. Klockans popover och listan på Inicio byggs av befintliga komponenter; ägaren godkänner skärmdump.
