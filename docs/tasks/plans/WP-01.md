# WP-01 · Kärnschema

Branch: `wp/WP-01-karnschema` · Status: **plan, godkänd 2026-09-27** · Beror på: WP-00 (☑) · Körs samtidigt som: WP-02 (ui), WP-03 (copy), WP-04 (scheduling), WP-05 (integrations). Se §3 om delade rotfiler.

## 1. Mål

Bygga det lokala kärnschemat för F1–F4 och F9 i Supabase (`businesses`, `memberships`, `staff`, `services`, `staff_services`, `business_hours`, `staff_hours`, `time_off`, `customers`, `bookings` med exclusion constraint, `payments`) med RLS och pgTAP för tenant-isolering per tabell, plus seed för "Barbería Norte". Paketet är databasdelen av två "klart när"-kriterier i MVP_SPEC: **F4** "två samtidiga bokningar av samma tid ger en lyckad och en med ett tydligt fel" (här bevisat på DB-nivå med två parallella transaktioner, felkod `23P01`) och **F3** "tillgängligheten respekterar alla lager (företag ∩ personal − frånvaro − bokningar − buffertar)" (här: alla lager finns som data, och buffert och bokningar blockerar i databasen). F1, F2 och F9 får sina tabeller här, och deras "klart när" uppfylls i WP-15, WP-13/WP-20 och WP-21.

### Steg 1: Lokal konfiguration (`supabase/config.toml`, `package.json`, `.prettierignore`, README)
- Stäng av oanvända lokala tjänster (K2), så att stacken startar snabbare och kräver mindre av Docker:
  - `[analytics] enabled = false`. Analytics/vector-containern är den som monterar Docker-socketen, så det minskar också beroendet av förkravet i steg 0.
  - `[edge_runtime] enabled = false`. Vi använder Next-routes, inte edge functions (D-003).
  - `[storage.s3_protocol] enabled = false` och `[storage.vector] enabled = false`. Storage i sig behålls (logotyper senare).
  - Realtime, Studio och `local_smtp` (magiska länkar lokalt) behålls.
- `[api] schemas = ["public"]`: ta bort `graphql_public`. GraphQL används inte, och pg_graphql exponerar annars schemaintrospektion. Samma värde föreslås för prod (§8).
- `project_id` och portar ändras inte (de delas av alla worktrees, se R1).
- `db:types` blir `supabase gen types typescript --local > src/types/database.ts.tmp && mv src/types/database.ts.tmp src/types/database.ts && prettier --write src/types/database.ts`. Utan det sista steget kan `format:check` i CI falla på den genererade filen. `.gitignore` har redan `src/types/database.ts.tmp`.
- Om den genererade filen ger lint-fel: lägg till `src/types/database.ts` i ESLint-ignore, men **bara** i så fall, och redovisa det i PR:en.
- `README.md`, ny sektion "Lokal databas": förkrav (Docker, socket), att bara en stack kan köras åt gången eftersom alla worktrees delar `project_id` och portar, `npm run db:reset` återskapar schema och seed, `test:db` kräver körande stack, och att inget körs mot moln.
- Skapa `docs/tech/SUPABASE_CONFIG.md` med tabellen "lokalt vs prod" från §8 (B5).

### Steg 2: Migration `core_foundation`
- `create extension if not exists btree_gist with schema extensions;` (krävs för `uuid with =` i exclusion constraint).
- `create schema private;` Schemat exponeras inte i Data API. Hjälpfunktioner för RLS läggs här i stället för i `public`, så att de inte kan anropas som RPC. `grant usage on schema private to authenticated;`
- Enum-typer: `member_role` (`owner`, `staff`, `vendor`, `admin`), `waitlist_mode`, `business_plan`, `business_status`, `deposit_kind`, `time_off_kind`, `booking_status`, `booking_source`, `payment_kind`, `payment_method`, `payment_status`, `consent_channel` (`web`, `whatsapp`, `manual`). Värden enligt DATA_MODEL.
- `private.set_updated_at()` (trigger, `set search_path = ''`).
- **Grants, försvar på djupet för INV-3:** `revoke all on all tables/sequences/functions in schema public from anon;` och `alter default privileges in schema public revoke all on tables, sequences, functions from anon;`. Dessutom `revoke execute on functions ... from public`. `authenticated` får uttryckliga grants per tabell i steg 3–7. Detta ligger i en migration, så samma sak gäller i prod.
- Kommentar överst i varje migration: vilket F# och vilka INV som berörs.

### Steg 3: Migration `businesses_memberships`
- `businesses` enligt DATA_MODEL, plus:
  - `slug`: `unique`, check `^[a-z0-9]([a-z0-9-]{1,38}[a-z0-9])$` och check mot en lista med reserverade ord som krockar med rutter (`app`, `api`, `r`, `admin`, `vendedor`, `login`, `design-lab`, `_next`, …).
  - `timezone`: default `'America/Santiago'`, check mot en lista med tillåtna zoner (v1: bara `America/Santiago`, D-011).
  - `phone` E.164-check (nullable), `accent_color` check `^#[0-9A-F]{6}$` (nullable, data och inte en stil i en komponent).
  - Checks: `min_notice_minutes >= 0`, `max_days_ahead between 1 and 365`, `cancel_window_hours >= 0`, `slot_interval_minutes in (5, 10, 15, 20, 30, 60)`.
- `memberships` enligt DATA_MODEL. `staff_id` via sammansatt FK `(business_id, staff_id) → staff (business_id, id)` läggs till i steg 4 när `staff` finns.
- `private.is_member(b uuid, roles member_role[] default null)`: `security definer`, `stable`, `set search_path = ''`, använder `(select auth.uid())`. Execute bara till `authenticated`.
- Trigger: det sista `owner`-medlemskapet i ett företag kan varken tas bort eller degraderas (annars blir företaget föräldralöst).
- `public.create_business(name, slug, comuna, category, phone) returns uuid` (se FRÅGA 3): `security definer`, `set search_path = ''`, kräver `auth.uid()`, skapar företaget och ägarens medlemskap i samma transaktion. Execute bara till `authenticated`.
- RLS, grants och policies (se FRÅGA 4 om rollerna):
  - `businesses`: select för medlemmar i alla roller, update för `owner`/`admin`. Ingen insert-policy (bara via `create_business`), ingen delete-policy.
  - `memberships`: select om `user_id = auth.uid()` eller om man är `owner`/`admin` i företaget. Insert, update och delete bara för `owner`/`admin` i företaget.

### Steg 4: Migration `catalog_and_hours`
- Alla tabeller får `business_id` + index, `unique (business_id, id)` där andra tabeller pekar hit, och **sammansatta FK** `(business_id, x_id) → x (business_id, id)`. Då kan en rad i företag A aldrig peka på personal, tjänster eller kunder i företag B, inte ens via service role. Avvikelse från DATA_MODEL: `staff_services` och `staff_hours` får kolumnen `business_id` (behövs för RLS och sammansatt FK). Se D-014 (förslag).
- `staff`: `color` lagras som **tokennamn**, check `color in ('staff-1', …, 'staff-6')` (tokens.css). Hex-värden lagras inte. `active` default true, `sort` integer.
- `services`: `duration_min > 0`, `price_clp >= 0`, `buffer_after_min >= 0`, `deposit_value >= 0`, check att `deposit_kind = 'none'` ⇔ `deposit_value` är null/0, `deposit_kind = 'percent'` ⇒ `deposit_value between 1 and 100`, `deposit_kind = 'fixed'` ⇒ `deposit_value <= price_clp`. `remind_after_weeks > 0` eller null.
- `staff_services (business_id, staff_id, service_id)`, pk `(staff_id, service_id)`, båda sammansatta FK.
- `business_hours (id, business_id, weekday, start_time, end_time)`: `weekday between 1 and 7` (ISO), `start_time < end_time`, och **ingen överlappning** mellan intervall samma dag (exclusion constraint med `int4range` av minuter eller trigger, db-engineer väljer). Flera intervall per dag är tillåtna.
- `staff_hours (id, business_id, staff_id, weekday, start_time, end_time)`: samma checks. Semantik enligt FRÅGA 5, som skrivs in i DATA_MODEL.
- `time_off (id, business_id, staff_id null, period tstzrange, kind, note)`: `not isempty(period)`, halvöppet intervall (`lower_inc and not upper_inc`), sammansatt FK för `staff_id`, gist-index på `(business_id, period)`.
- RLS och grants på alla sex tabeller: select för `owner`/`admin`, write för `owner`/`admin`.

### Steg 5: Migration `customers`
- Enligt DATA_MODEL, plus:

  - `name` not null utom när anonymiserad. `email` enkel formatcheck, nullable.

### Steg 6: Migration `bookings_payments`
- `bookings` enligt DATA_MODEL, med sammansatta FK till staff, service och customer, plus:
  - `period` och `blocked`: not null, inte tomma, halvöppna, `lower(blocked) = lower(period)`, `blocked @> period`.
  - Pengar: `price_clp >= 0`, `discount_clp between 0 and price_clp`, `deposit_clp between 0 and price_clp - discount_clp`.
  - Status: `pending_payment` ⇔ `pending_expires_at` satt, `cancelled` ⇔ `cancelled_at` satt.
  - `manage_token`: enligt FRÅGA 6, antingen `text unique` enligt DATA_MODEL eller (rekommenderat) `manage_token_hash bytea unique`.

**D-014 (förslag) · Tenant-integritet och åtkomst i databasen.** (Numret sätts av orkestreraren om andra planer också föreslår beslut.)
*Beslut:* (1) alla tenant-tabeller har `business_id` och refererar varandra med sammansatta FK `(business_id, id)`, (2) RLS-hjälpfunktioner ligger i schemat `private` (inte exponerat), är `security definer` med `search_path = ''`, (3) `anon` har inga grants alls i `public`, och `authenticated` får uttryckliga grants per tabell, (4) nya företag skapas bara via `create_business()`. *Varför:* RLS skyddar mot fel användare, men inte mot en serverbugg som med service role kopplar ihop rader från två företag. Sammansatta FK gör det omöjligt. *Konsekvens:* varje ny tabell följer mönstret, och schemavakten i `000_schema_guard.test.sql` fångar avsteg.

## 5. Tester

**DB (pgTAP), en fil per tabell plus tvärgående tester**

`000_schema_guard.test.sql`, tvärgående och fångar framtida tabeller:
- Varje tabell i `public` har `relrowsecurity = true`.
- Ingen policy i `pg_policies` har rollen `anon` eller `public`.
- `anon` har inga tabell-, sekvens- eller funktionsprivilegier i `public` (`has_table_privilege` över alla tabeller).
- Varje `security definer`-funktion i `public` och `private` har `search_path` satt (`proconfig`).
- Varje tabell med kolumnen `business_id` har ett index som börjar på `business_id`.
- `btree_gist` är installerat. `no_overlap` finns på `bookings` och är av typen exclusion.

**Tenant-isolering (INV-4), samma mall för var och en av de elva tabellerna** (`010_businesses`, `011_memberships`, `020_staff`, `021_services`, `022_staff_services`, `023_business_hours`, `024_staff_hours`, `025_time_off`, `030_customers`, `040_bookings`, `050_payments`):
1. `ownerA` ser A:s rader och **noll** av B:s (`results_eq` på count).
2. `ownerA` kan inte göra insert med `business_id = B` (`throws_ok … '42501'`).
3. `ownerA` gör update/delete på B:s rader, 0 rader påverkas och B:s data är oförändrad (kontrolleras som postgres efteråt).
4. `ownerA` kan inte flytta en egen rad till B (update `business_id = B` → `42501`).
5. `anon`: select, insert, update och delete ger `permission denied` (`42501`).
6. `staffA` och `vendorA`: enligt FRÅGA 4 (rekommendation: noll rader i allt utom den egna `memberships`-raden och `businesses`-raden, och inga skrivningar).
7. En användare utan medlemskap ser noll rader.
8. **Tvärtenant-FK:** som postgres (förbigår RLS) misslyckas en rad i A som pekar på staff/service/customer/booking i B med `23503`. Det bevisar de sammansatta FK:erna.

Tabellspecifikt utöver mallen:
- `010_businesses`: `create_business()` skapar företag och ägarmedlemskap. `anon` kan inte anropa den. Ogiltig/reserverad slug (`api`, `Barberia`, `-x`) och dubblettslug ger fel. `staffA` kan inte uppdatera företaget.
- `011_memberships`: `staffA` kan inte uppgradera sig själv till `owner`. `ownerA` kan inte lägga till medlemskap i B. Sista ägaren kan inte tas bort eller degraderas, men det går när det finns två ägare.
- `020_staff`: färg `#C9B8F5` eller `staff-7` avvisas.
- `021_services`: `duration_min = 0`, negativt pris, `percent` 0 eller 101 och `fixed` större än priset avvisas.
- `023/024_*_hours`: `weekday` 0/8, `start >= end` och överlappande intervall samma dag avvisas. Två intervall samma dag utan överlapp (10–13:30, 14:30–19) accepteras.
- `025_time_off`: tomt intervall och slutet intervall `[a,b]` avvisas. `staff_id = null` accepteras.
- `030_customers`: ogiltig telefon (`56912345678`, `+56 9 1234 5678`, `+0…`) avvisas. Dubblett (business, phone) avvisas, men samma telefon i A och B är okej. **Samtycken är null efter en insert utan samtyckesfält** (aldrig förkryssat). `consent_terms_at` utan version avvisas. `phone_e164 = null` utan `anonymized_at` avvisas.
- `050_payments`: `amount_clp = 0`, `approved` utan `paid_at` och dubblett `(method, provider_ref)` avvisas. Ingen delete för `ownerA`.

**Exclusion constraint (INV-1), `041_bookings_no_overlap.test.sql`**
- Samma profesional med överlappande `blocked` → `23P01`.
- Kant mot kant: `[10:00,10:35)` och `[10:35,11:25)` → båda okej (halvöppet).
- Buffert: tjänst med 10 min buffert, bokning A `period [10:00,10:35)`, `blocked [10:00,10:45)`. B som börjar 10:40 → `23P01`. B som börjar 10:45 → okej.
- Olika profesionales samma tid → okej.
- `cancelled` och `no_show` blockerar inte: en ny bokning i samma tid är okej. `pending_payment` och `completed` blockerar.
- Återaktivering: update från `cancelled` till `confirmed` när tiden är tagen → `23P01`.
- Flytt: update av `period`/`blocked` in i en annan bokning → `23P01`.
- `blocked` som inte börjar samtidigt med `period` eller inte innehåller den → check-fel. Negativ rabatt, rabatt > pris och handpenning > pris − rabatt → check-fel. `pending_payment` utan `pending_expires_at` → check-fel.

**Samtidighet (F4 "klart när" på DB-nivå), `042_bookings_concurrency.test.sql`**
- Med `dblink` (skapas i testet) öppnas två separata anslutningar. Anslutning 1: `begin`, insert av bokning X (staff S, 11:30–12:05), ingen commit. Anslutning 2: `dblink_send_query` med en insert av bokning Y (staff S, 11:45–12:20), som blockeras. Anslutning 1 gör `commit`. Resultatet för anslutning 2 hämtas och ska vara felet `23P01` (`no_overlap`). Exakt en rad finns.
- Omvänd ordning (anslutning 1 gör `rollback`): anslutning 2 lyckas.

## 6. Risker och öppna frågor

**Risker**
- **R1. En lokal stack åt gången.** Alla worktrees delar `project_id = "OrdenaGroup"` och portarna, alltså samma containrar och volymer. Om en annan worktree kör `db:reset` med sin (tomma) `migrations/` raderas WP-01:s schema lokalt, och tvärtom. Därför kör bara WP-01 lokal Supabase i Våg A (FRÅGA 2). Efter merge har alla worktrees samma migrationer via `main`. Unika `project_id` och portar per worktree är möjligt men ändrar `.env.example`, och det lämnas till IDEAS.
- **R2. Docker-socket.** Utan förkravet i steg 0 kan `supabase start` falla. Att stänga av analytics i steg 1 tar bort den vanligaste orsaken, men ägaren behöver ändå slå på inställningen.
- **R3. dblink i samtidighetstestet.** dblink kräver lösenord när anslutande roll inte är superuser, och `postgres` i Supabase-imagen är inte fullständig superuser. Om `dblink_connect` inte går att använda flyttas samtidighetstestet till WP-10 (se §5). Constraint-beteendet är ändå bevisat sekventiellt i `041`.
- **R4. `\ir` i pg_prove.** Om `supabase test db` inte stöder include dupliceras hjälparna. Det är kosmetiskt.
- **R5. Seed i `auth.users`.** Direktinsert beror på GoTrues interna kolumner, som kan ändras mellan CLI-versioner. Om det blir bräckligt stryks raden (se steg 8).
- **R6. `staff_hours` kan bli bredare än `business_hours`.** Det händer om ägaren snävar in företagets tider i efterhand. Databasen hindrar det inte. Schemamotorn (WP-10) räknar alltid snittet, så det blir aldrig fel för kunden. UI:t i WP-15 bör varna.
- **R7. Räknare som glider.** `visits_count`/`no_show_count` är denormaliserade. WP-21 måste uppdatera dem i samma transaktion som statusbytet (eller med en trigger). Annars stämmer inte F9. Detta noteras i DATA_MODEL.
- **R8. Designdata går isär.** `Main.dc.html`/`Hoy.dc.html` visar andra kunder på fredagen (t.ex. Valentina Soto 15:45, Emilio Tapia 18:00) än `Agenda.dc.html`. Seed följer Agenda (enligt db-engineer.md). UI-skärmarna använder egna fixturer i design lab, så det påverkar inte visual.
- **R9. `format:check`/lint på genererade typer.** Hanteras med `prettier --write` i `db:types` (steg 1).
- **R10. Prod är inte konfigurerad av config.toml.** `config.toml` gäller bara lokalt. Prod-värdena i §8 måste sättas manuellt av ägaren (eller med `config push`, som är spärrat för agenter). Annars gäller Supabase-standard (t.ex. inbyggd SMTP med 2 mejl/timme).
- **R11. Postgres-version.** Lokalt `major_version = 17`. Prod-projektet måste skapas med PG 17, annars skiljer sig beteendet.
